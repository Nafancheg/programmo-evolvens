# Прикладной сценарий: Excel → итоговая матрица

[English](../en/10-excel-to-matrix.md) · [Главная](../../README.md) · [To-do](../../planning/phase-1.md)

**Источник:** постановка пользователя 2026-10-31. **Статус:** сценарий зафиксирован; реальные файлы, эталоны и правила приёмки ещё не предоставлены. Цель — практическое получение нужных данных через автономный поиск решений. Существующие примеры прототипа этот сценарий не реализуют.

## Задача

Пользователь предоставляет набор входных Excel-файлов и соответствующие итоговые матрицы, подготовленные вручную или другой программой. Внутренний способ преобразования заранее не предписывается. Система должна находить способ чтения, интерпретации, сохранения, актуализации, систематизации и дальнейшего преобразования данных, который даёт требуемый результат.

Рабочая схема: **Excel → извлечение и интерпретация → сохранение/обновление → систематизация и преобразование («ферментация») → итоговая матрица → сравнение с эталоном**. Это описание ответственности, а не утверждённый алгоритм или требование отдельных компонентов на каждый этап.

Возможное содержимое «ферментации» — сопоставление сущностей, нормализация, вычисления, объединение источников, агрегирование, группировка. Какие из этих действий нужны, определяется примерами и требованиями пользователя; пока это варианты, не согласованные правила.

## Проверочные примеры

Для разового преобразования пример содержит входной файл или набор файлов и ожидаемую матрицу. Для актуализации пример содержит **исходное сохранённое состояние + последовательность поступающих файлов → ожидаемые состояния и матрицы после обновлений**. Это позволит проверить не только первый импорт, но и поведение при следующих поступлениях.

Нужно согласовать смысл повторного импорта, исправленных строк, дубликатов, отсутствующих значений и удаления записей. Ключи записей, правила приоритета источников и удаления не предполагаются автоматически. Разные последовательности с одинаковым итогом не обязательно эквивалентны: требуемую семантику определяют эталоны.

## Сравнение с эталоном

До запуска поиска определить:

1. Состав и смысл выходных колонок, ключи сопоставления строк и значимость порядка.
2. Правила для типов, дат, единиц, округления, пустых значений и допустимых отклонений. Сравнивать содержание; оформление файла учитывать только если оно входит в требования.
3. Обязательные условия: например, отсутствие потери и удвоения записей, корректность обновлений. Конкретный список устанавливается по задаче.
4. Критерий достижения результата и бюджет времени, попыток и вычислений. Средний балл не должен скрывать провал обязательного условия.

Часть пар используется для поиска вариантов, часть — для отдельной проверки на новых файлах. При повторных запросах к проверочному набору он перестаёт быть независимым; окончательную оценку нужно отделять от обратной связи поиску. Совпадение на известных примерах не доказывает восстановление единственно правильного правила для всех будущих файлов.

## Автономный цикл

Контур поиска создаёт изменённые варианты решения, запускает их на примерах, получает ошибки и оценки от фиксированного проверяющего механизма, сохраняет происхождение вариантов и выбирает родителей следующих кандидатов. Проверяющий механизм и эталоны кандидатам изменять нельзя. Архив позволяет сохранять перспективные ветви, даже если текущий вариант не лучший.

Система останавливается при достижении согласованных критериев либо бюджета. Во втором случае сообщает лучший результат и оставшиеся расхождения, не объявляя задачу выполненной. После поиска выбранный вариант отдельно проверяется на отложенных данных.

Текущее JSON v0 поддерживает только скалярные порты и ограниченные операции; оно пока не задаёт пространство решений для этого сценария. Выбор готового эволюционного инструмента, расширение декларативной модели и создание вариантов кода требуют отдельной оценки. Допуск генерируемого кода не считается автоматически согласованным изменением ADR-001/002.

## Первый практический результат

Получить проверяемое преобразование реальных файлов в требуемую матрицу, включая обновление данных, и сравнить самостоятельный поиск с исходным решением при одинаковых условиях. Зафиксировать корректность, ошибки, время и стоимость поиска, а также проверки на новых файлах. Это оценка прикладной полезности; научная уникальность не является условием принятия полезного результата.
